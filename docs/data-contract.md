# PlantVision — Data Contract

This is the contract every capture, ingest, processing, and analysis component must honor.
Nothing may be written to the database or to `data/originals/` that violates it.
Mirrors the DDL in `src/plantvision/storage/schema.sql`; if this file and the DDL disagree,
that is a bug — fix one of them.

## 1. The 7 required observation fields

Every accepted frame produces exactly one observation record with these fields:

| # | Field | Type | Meaning | Rules |
|---|-------|------|---------|-------|
| 1 | `image_id` | TEXT (uuid4 hex) | Server-generated unique content identifier, assigned on first receipt. Never re-used. | Generated by the server from a `uuid4().hex`; NOT a hash of the pixels (that is `sha256`), NOT client-supplied. |
| 2 | `captured_at` | TEXT (ISO-8601 UTC) | When the frame was taken, by the **device clock** on the phone. | Phone timezone is fixed and known (tz rule §5); converted to UTC at ingest. NOT the arrival time. |
| 3 | `camera_id` | TEXT | Which physical camera produced the frame. | One camera at Stage 0–6 (`phone-01`); format `make-model-NN` or similar stable slug. |
| 4 | `zone_id` | TEXT | Which location in the farm the camera points at. | One zone at Stage 0–6 (`shelf-a/tray-1`); format `<area>/<unit>` slug. |
| 5 | `image_path` | TEXT | Relative path of the original under `data/originals/`. | Relative to repo root; e.g. `data/originals/2026/10/13/<image_id>.jpg`. Original bytes are never modified. |
| 6 | `capture_status` | TEXT, one of `ok` \| `corrupt` \| `duplicate` | Outcome of the capture/ingest health check. | `ok` = decodable frame, in light window; `corrupt` = bytes present but not decodable/incomplete; `duplicate` = bytes whose sha256 already exists (recorded, no second file, see §3). |
| 7 | `processing_status` | TEXT, one of `pending` \| `running` \| `done` \| `failed` \| `skipped` | Whether the CV pipeline has processed this observation. | Lives in the `processing` table keyed by `(image_id, pipeline_version)`; see §4. One observation can have a different status per pipeline version. |

## 2. Timestamps: `captured_at` vs `received_at`

Both columns exist and neither is optional:

| Column | Table | Clock | Set when | Notes |
|---|---|---|---|---|
| `captured_at` | `snapshot` | **device clock** (phone) | Frame captured by IP Webcam | Taken from the capture response/sidecar; converted to ISO-8601 **UTC** at ingest. |
| `received_at` | `snapshot` | **server clock** (Ubuntu) | Bytes fully persisted to `data/originals/` | Written at ingest time. |

- Storage format for both: ISO-8601 **UTC**, e.g. `2026-10-13T18:24:37.412Z`.
- Never infer one from the other. Resyncs of the phone clock can create jitter in
  `captured_at`; the intervals are analyzed with that in mind.
- Local-clock reference for the light window: see §5.

## 3. Idempotency rule: sha256 of raw bytes

- **Key**: SHA-256 of the *raw image bytes as received* (before any resize/re-encode).
  Stored in `snapshot.sha256`, `UNIQUE`.
- **Rule**: before inserting, the ingest path checks whether that sha256 already exists.
  If it does:
  - no new row is inserted;
  - no second file is written;
  - nothing is destroyed — if it is useful for diagnostics, a record with
    `capture_status='duplicate'` may reference the existing `image_id`;
    otherwise the duplicate is silently ignored.
  - Definition: `capture_status='duplicate'` means *bytes whose sha256 already exists in
    `snapshot`* — a re-send of identical content (e.g. a retry after a timeout where the
    first attempt was actually received, or a pull hitting a cached identical resource).
  Two *different* photos of the same plant are NEVER duplicates; only identical bytes can be.
- This is the behavior that makes re-delivery safe: if a send is retried and the
  server already processed the same bytes, re-sending must be a no-op.

## 4. The 4 storage entities

(Low-level storage view; field rules above still apply. The full DDL is
`src/plantvision/storage/schema.sql`.)

| Entity | Purpose | Grain (one row is…) |
|---|---|---|
| `snapshot` | One accepted upload of bytes + its observation metadata. The spine. | …one received image, identified by `image_id`. |
| `processing` | One pipeline run's state for one image. | …one `(image_id, pipeline_version)` pair: pending/running/done/failed/skipped for a given pipeline version. |
| `measurement` | One metric value extracted from one image by one pipeline version. | …one `(image_id, pipeline_version, metric_name)` scalar, with unit and `computed_at`. |
| `model_version` | Registry of model/threshold versions. | …one released model configuration (`model_version`, `model_path`, `params_json`). |

- Relations: `processing.image_id` and `measurement.image_id` are FKs to
  `snapshot(image_id)`, `ON DELETE CASCADE` — deleting a snapshot removes its processing
  rows and measurement rows, while `model_version` stands alone.
- Observations and measurements are **append-only** in normal operation; nothing is
  updated except `processing.processing_status` transitions (and `processed_at` /
  `error_message` when they finish).

## 5. Timezone rule

The phone timezone is fixed and known for the lifetime of a deployment (no auto-DST
churn, no travel). All timestamps are **stored in UTC**, converted at ingest;
display in the UI renders in UTC or explicitly in the farm-local timezone (`tz: local`
in `configs/capture.yaml`), never in a silent mix.

The photoperiod `light_window` in `configs/capture.yaml` uses **farm-local time**
(06:00–22:00 default; start inclusive, end exclusive). Context for `dark_policy`:
RGB frames taken in darkness cannot support growth metrics, so `dark_policy: skip`
skips the dark window entirely.

## 6. What must NOT be done

- No new required fields without extending this contract first, and mirroring it in `schema.sql`.
- No deletion of originals in normal operation (retention belongs to `data/README.md`).
- No storage of un-hashed image content in the DB — the DB stores metadata and paths only.
- No re-sizing or re-encoding of bytes *before* the sha256 is computed — the idempotency key
  must be over the bytes as they are actually persisted.
